# 測試入口

`npm run verify` 執行 lint、全部 Vitest 案例、產品程式與測試的 typecheck 與 Node／Web build；CI（`ci.yml`）在 Mac 上先 `npm run download:runtime` 再跑它，真實引擎案例一起執行。`npm test` 只跑測試，`npm run test:watch` 用於開發。測試檔由 `tests/**/*.test.ts` 收集。測試（含 `tests/support`）以 `tsconfig.tests.json` 做 typecheck（`npm run typecheck:tests`，verify 執行它，`build` 不執行），與產品程式同樣嚴格，所以呼叫產品函式漏傳必填參數時 verify 失敗；測試 import 的 `scripts/` 與 verify skill 的 `.mjs` 沒有型別宣告，該 import 標 `@ts-expect-error`。測試沒有全域的來源類型：需要來源類型的測試把 `tests/support/product-sources.ts` 的 `PRODUCT_SOURCES`（產品類型的 registry）傳給受測物件；用假類型的測試以 `productSourcesWith(...)` 或 `sourceRegistry(...)` 建自己的 registry。

## 測試放哪裡

單元與整合測試的路徑就是受測的 src 檔路徑：`src/domain/jobs/job-queue.ts` 的測試是 `tests/domain/jobs/job-queue.test.ts`，`src/transport/server/routes/documents.ts` 的是 `tests/transport/server/routes/documents.test.ts`。HTTP 行為測試對應它走的 route 檔；Host 檢查、遮蔽與 Vault 存取這類每個請求都經過的 hook 對應 `src/transport/server/app.ts`。一個 src 檔有多支測試時檔名寫成 `<src 檔名>.<面向>.test.ts`，例如 `tests/transport/server/app.masking.test.ts`。跨好幾個模組的測試放在它斷言的行為所屬的模組，也就是要讓它失敗得改的那個檔。

`scripts/` 的工具同樣鏡像，放在 `tests/scripts/`：`scripts/package/package-app.mjs` 的測試是 `tests/scripts/package/package-app.test.ts`，多支測試時一樣寫成 `<檔名>.<面向>.test.ts`，例如 `tests/scripts/lib/owned-directory-lock.race.test.ts`。

不對應單一檔案的只有兩處：`tests/tooling`（repo 規則的掃描）與 `tests/support`（共用 helper，不是測試）。測試自己的 fixture 放在測試旁的 `fixtures/`。`tests/tooling/test-paths.test.ts` 在測試對不到 src 或 `scripts/` 的檔案時失敗，列出每個測試與它預期的路徑。

## 等待

等待與證明「沒有發生」的規則見 [專案驗證設定的測試等待](../docs/project-validation.md#自動檢查)。可直接等的 promise 例如 `JobManager.whenSettled` 與假來源的 `holds.started()`；其餘用 `tests/support/wait.ts` 的 `eventually`。證明沒有發生的寫法，例如等 gate 裡後排的請求跑完，再確認逾時的預覽沒有送出；或等 server 的 listener 關閉，再確認 close 仍在等 handler。測試替身用固定時間模擬工作耗時，只放在 `tests/support/`；其他測試的直接計時由 lint 擋下。需要時間的產品模組由測試傳入 `tests/support/timers.ts` 的計時器（`timersAfter` 由測試決定何時觸發，`stoppedTimers` 永不觸發），不真的等待。

分類不代表測試層級：同一功能可能包含單元、HTTP 與檔案系統整合。`web` 的函式測試不是完整畫面 E2E，yt-dlp 的 fixture 測試也不是 YouTube 真實連線驗收。Web 畫面與原生操作的驗證層級依 [專案驗證設定](../docs/project-validation.md#驗證層級)，只在有實際自動化案例時建立 E2E 測試目錄。

## 真實搜尋與平台邊界

真實引擎案例帶 vitest tag `real-engine`（`tests/support/real-engine.ts`），依平台使用釘住的 binary：Mac arm64 是 `npm run download:runtime` 安裝的 `resources/bin/mac/meilisearch`，Windows x64 是 `npm run download:runtime:win` 安裝的 `resources/bin/win/meilisearch.exe`（旁邊要有 `scripts/runtime/prepare-windows-crt.mjs` 放的 `vcruntime140.dll`，或機器已安裝 Visual C++ runtime）。這兩個交付平台以外的平台略過這些案例；交付平台缺少 runtime 時案例失敗並印出該平台的安裝指令，不會略過。`npm run test:meilisearch:mac` 下載 runtime 後只跑這些案例。

`.github/workflows/meilisearch-native.yml` 在 Mac arm64 與 Windows x64 runner 下載固定的 Meilisearch release（Windows 另放上 repo 內的 `vcruntime140.dll`），再用臨時 database 驗證 canonical settings、中文／英文索引、filter、page、highlight/crop 與 restart persistence。這組 native smoke 與一般 Vitest 分開，不能用模擬 runner 或單元測試取代，也不是正式 Release 安裝包的來源。

交付平台增加時一起調整 binary 選擇與 skip 規則；不以 fixture 冒充另一平台通過。

依賴 POSIX 行為的案例（檔案權限位元、`/bin/ps`、POSIX signal、以 shebang 啟動的程式）以 `it.skipIf(process.platform === 'win32')` 在 Windows 略過，在 Mac 照常執行；Windows 沒有這些行為，不以 mock 冒充通過。反過來，`shared/lib/json-file.test.ts` 以 PowerShell 開著目標檔、不允許刪除，重現 Windows 拒絕取代的 rename，只在 Windows 執行。Agent 金鑰檔的保護在 Mac 檢查權限位元、在 Windows 以 PowerShell 讀檔案的存取規則並與同資料夾的一般檔案比對，同一個案例兩個平台都執行；`domain/search/meilisearch-process.leftover.test.ts` 的「被結束的 App 留下 Meilisearch」案例只在 Mac 執行：Windows 上 libuv 把沒有 `detached` 的子程序放進 job object，父程序結束時一起結束，不會留下引擎。`domain/search/meilisearch-process.test.ts` 的程序辨識只在 Mac 執行，Windows 上啟動時只刪 pid 檔。Windows 的一般帳號不能建 symlink，symlink 防護的案例在 Windows 改建 junction（lstat 也把它讀成 symlink），在 Mac 與 Linux 照常建 symlink。比對 Git 回報的路徑時，暫存目錄先經 `realpathSync.native`，展開 macOS 的 `/var` symlink 與 Windows 的 8.3 短檔名。PR 門檻只在 Mac 執行，Windows 的部分由 nightly 與 Windows 上的完整 verify 涵蓋。這些邊界要在另一個平台跑完整 `npm run verify` 才看得到，時機見 [專案驗證設定](../docs/project-validation.md#另一個平台的完整驗證)。

verify skill 函式庫自己的測試在 `.claude/skills/verify/tests/`，以 `npm run test:verify-skill` 執行，不在 `npm run verify` 中；PR CI 只在改動碰到 `.claude/skills/verify/scripts/` 或 `.claude/skills/verify/tests/` 時跑。startup 檢查（`.claude/skills/verify/scripts/startup.mjs`）啟動開發版 Electron 或 `--app` 指定的打包版，在 Mac 或 Windows 執行。內容見 [verify skill](../.claude/skills/verify/SKILL.md#自我測試)。
