# 收集流程

從加入訂閱到文件保存，收集工作經過排程、佇列與來源的請求通道，遇到錯誤時等待或結束，檢查結束後記入訂閱。本文件說明各步的規則與原因；次數、間隔與上限是程式中的常數，畫面文字由 presentation 模組決定，這裡只寫名稱與位置。

| 部分 | 程式 |
| --- | --- |
| 排程 | `src/domain/subscriptions/scheduler.ts` |
| 工作的執行與回報 | `src/domain/jobs/job-manager.ts`；回報給訂閱的內容在 `src/domain/jobs/subscription-reports.ts` |
| 佇列與 lane 的順序 | `src/domain/jobs/job-queue.ts` |
| 重啟接續 | `src/domain/jobs/job-recovery.ts` |
| 檢查收集哪些項目（候選規則） | `src/domain/subscriptions/candidates.ts` |
| 等待條件與其計時器 | `src/domain/jobs/job-waits.ts` |
| 請求通道與冷卻 | `src/domain/pacing/pacing-gate.ts` |
| 斷網與睡眠 | `src/domain/jobs/connectivity.ts`、`src/shared/jobs/collection-pause.ts`；桌面版另有 `src/desktop/electron/network-watch.ts`、`sleep-watch.ts` |
| 檢查結束、項目失敗與連續失敗的計入 | `src/domain/subscriptions/subscription-service.ts` |
| 狀態 | `src/domain/jobs/job-board.ts`（`workStatus`）、`subscription-service.ts`（`checkStatus`） |

## 工作

一個 Vault 一個 `JobManager`。工作有三種角色：

- `add`：辨識訂閱網址、訂閱，並派出第一次檢查。
- `check`：列出訂閱的項目，為每個要收集的項目排一個 `item`，等它們全部結束。
- `item`：收集一個項目，保存文件並更新搜尋。

同一個項目、訂閱或訂閱網址同時只有一個未結束的工作，重複送出時併入進行中的那個。使用者直接送出一個檢查正在收集的項目時，它改為使用者自己的請求，不受訂閱暫停與收集範圍限制。

## 排程

每個訂閱有自己的下次檢查時間。排程定時輪詢，把到期的訂閱一起送出，一個訂閱一個 `check`，不等它們完成；訂閱已有進行中的檢查時併入它。一次到期只由一個檢查滿足：訂閱最近一次檢查在這次到期之後才開始列出來源時，定時檢查併入它，即使它已經結束，例如斷網前派出、恢復後才實際列出來源的檢查。這筆「開始列出來源的時間」只存在記憶體，App 重啟後重新計算，所以重啟前後最多多檢查一次。定時檢查維持訂閱自己的節奏，輪詢延遲不累積，錯過的週期也不逐一補檢查。重新開啟自動檢查時，已過的時間從開啟時起算，所以長時間關閉後不會同時全部到期。

暫停的訂閱、自動檢查關閉、收集暫停期間都不派定時檢查；收集暫停解除時立即看一次到期的訂閱。

## 檢查收集哪些項目

檢查從新到舊讀訂閱的清單。候選是收集範圍內最新的 `maxItems` 個合格項目；其中已收集、已刪除或已知在範圍外的不收，其餘收集。不收的候選不由更舊的項目遞補，所以一次檢查不會收集範圍內最新 `maxItems` 個以外的項目。讀到第一個早於範圍的項目，或候選已滿，就停止讀取，來源只列出檢查需要的部分。

被排除的項目（在起點不早於當初的範圍內判定為範圍外的，以及失敗後略過的）與已有文件的項目仍算候選、不收集，所以照樣佔項目上限。

清單上的發佈時間可能不精確：沒有發佈時間的項目算在範圍內，擷取時再以 `publishedNotBefore` 確認實際時間。

## 佇列與請求通道

佇列分兩條，同時執行的數量與佇列上限見 `DEFAULT_JOB_LIMITS`：

- **列出**：`add` 的辨識與 `check` 的列出。
- **收集**：`item`。每個檢查排的項目是一條 lane，單一網址的項目自成一條；收集在 lane 之間輪流，大的訂閱不會佔住所有名額。

每個來源類型有一條請求通道（pacing group），該類型所有請求都經過它：一次一個，請求之間隔一段隨機等待，從上一個請求結束時起算，時間沒有固定節奏。使用者在等的請求（預覽）排在背景工作之前。等待範圍在各 plugin 的 `pacing` 宣告。

工作開始後不再回到「排隊中」：等待重試或冷卻的工作顯示為重試中。

## 錯誤的分類

來源以 `classifyFailure` 把錯誤碼分成五類，各 plugin 的 `FAILURES` 決定對應：

| 分類 | 處理 |
| --- | --- |
| `retry_now` | 同一個工作稍後自動重試 |
| `rate_limited` | 等通道的冷卻結束，不算一次嘗試 |
| `retry_next_check` | 工作失敗；檢查中的項目留給下次檢查再試 |
| `skip` | 工作失敗；檢查中的項目之後都略過 |
| `login_required` | 工作失敗；不計入項目與訂閱的失敗 |

`FAILURES` 沒有對應的錯誤碼歸為 `skip`。目前的 plugin 都沒有對應到 `login_required` 的錯誤碼。

`network_error` 先確認裝置有沒有網路：沒有網路就進入收集暫停，工作退回佇列；有網路才算一次失敗，讓單一來源連不上時照常失敗。發佈時間早於收集範圍、文件已刪除，以略過結束，不是失敗。

## 等待

排隊中的工作有三種等待條件，條件解除後自己繼續：

| 條件 | 範圍 | 開始 | 解除 | 排回佇列 |
| --- | --- | --- | --- | --- |
| 收集暫停 | 整台裝置（hold 為一個 Vault） | 斷網、系統睡眠、知識庫操作、準備套用 App 更新 | 原因全部解除 | 最前面 |
| 冷卻 | 一個 pacing group | 來源限流 | 冷卻時間到 | 最前面 |
| 重試時間 | 一個工作 | `retry_now` 的失敗，且還有嘗試次數 | 下次嘗試時間到 | 最後面 |

被暫停或冷卻打斷的步驟本來輪到了，所以排回最前面；重試的工作在等待期間讓出名額給其他工作，時間到才排到最後面。

### 重試

次數與間隔見 `DEFAULT_RETRY_POLICY`。嘗試次數記在工作的 `retry`，跨重啟保留，重啟不會多給次數。次數用完時工作失敗；檢查中的項目改以 `retry_next_check` 記入訂閱。

### 冷卻

一個來源限流時，同一通道的其他請求多半也會被限，所以整個通道冷卻：不送任何請求，排隊等通道的請求（包括預覽）立即以 `rate_limited` 失敗。冷卻長度隨連續限流加倍，成功一次或隔得夠久就重來，見 `DEFAULT_COOLDOWN`。冷卻期間，該通道排隊中的工作與新接受的工作都帶 `wait`，其他通道照常。冷卻狀態存在 profile，重啟後沿用。

RSS 的每個 feed 是不同的網站，一個 feed 限流不代表其他 feed 也會，所以 RSS 通道不冷卻（`cooldown: false`）：限流只讓那一個請求失敗，分類為 `retry_next_check`。

### 斷網與睡眠

收集暫停是整台裝置一個開關（`CollectionPause`），原因有 `offline` 與 `sleep`；知識庫操作（匯出、匯入、建立新的知識庫、開啟其他知識庫）與準備套用 App 更新以 `hold`（`src/domain/vault/operation-lock.ts`）對單一 Vault 產生相同效果。

- 在線時不定時探測。請求以 `network_error` 失敗時確認網路；桌面版讀到作業系統對網路的判斷改變（例如 Wi-Fi 斷線或連上）時也立即確認，因為作業系統的判斷只反映網路介面，不代表連得到外部網站。這個判斷定時讀取（`network-watch.ts` 的 `NETWORK_WATCH_MS`），讀取不發出任何請求。斷網期間定時再確認，睡眠中不確認，喚醒時立即確認；這些間隔見 `connectivity.ts` 的常數。
- 確認時同時向兩家廠商的固定回應網址發出請求，任一家回應正確就算在線，所以單一廠商故障或被擋不會被當成斷網。請求不帶 cookie、帳號或訂閱資訊。
- 暫停期間不派檢查、不開始新步驟；等通道的步驟放棄等待，已送出的請求跑完，若因暫時性錯誤失敗也退回佇列，不算一次嘗試。
- 需要網路的操作（送出網址或單一項目、辨識網址、新增訂閱、預覽、重試）在斷網時以 `offline` 拒絕，不建立工作；立即檢查先重新確認網路，仍然斷網才拒絕。訂閱不會因斷網顯示錯誤。
- 暫停不寫入檔案，重啟後從在線開始。

## 檢查結束

檢查在所有項目結束後才結束；項目失敗不會讓檢查失敗。工作照實回報項目的失敗與檢查的結束，附上來源類型對錯誤的分類，以及只有工作知道的事：檢查是否被暫停、移除，或因多次中斷而停止接續。哪些失敗計入、計入後如何記錄，由訂閱決定。

**項目的失敗**記在訂閱上，跨檢查累計：`skip` 或累計到 `MAX_CHECK_ATTEMPTS` 時標為略過，之後的檢查不再嘗試；收集成功或離開收集範圍時清除。等冷卻的限流（`rate_limited` 分類）與需要重新登入不算項目的失敗；RSS 的限流分類為 `retry_next_check`，照常計入。

**檢查的失敗**是列出失敗。檢查結束時記錄檢查時間並更新連續失敗；被暫停、移除或較新工作接手而略過的檢查，以及只重試失敗項目的工作，不回報結束，兩者都不記錄：

- 成功清除連續失敗，失敗加一次。失敗的檢查不列在工作頁的失敗區，由訂閱列顯示。
- 只記錄檢查時間、不改連續失敗：檢查期間訂閱被暫停或移除、需要重新登入（影響同類型的所有訂閱，不是這個訂閱的問題），以及因多次中斷而停止接續的工作。
- 連續失敗達 `AUTO_PAUSE_FAILURES` 次，且第一次距今至少 `AUTO_PAUSE_AFTER_MS`，訂閱自動暫停。兩個條件同時成立才暫停，所以短時間內的一連串失敗，以及間隔很長但次數不到的失敗，都不會暫停。
- 恢復訂閱時清除連續失敗，並立即檢查一次。

## 改設定與移除訂閱

- 啟用中的訂閱改間隔時，下次檢查從上次派工起算，已過就立即到期；改收集範圍套用到之後開始列出的每個檢查，包括已排隊的。改設定不開始任何工作。
- 把設定套用到同類型的其他訂閱時，暫停中的也套用並保持暫停，之後恢復所開始的檢查就用新設定。
- 預覽辨識過的網址暫存一段時間，預覽後隨即新增訂閱時不再辨識一次；沒預覽過或預覽太久以前的網址重新辨識。
- 移除訂閱可保留或刪除它的文件。刪除時，訂閱還在擷取中的項目（任何一次檢查的，包括已停止的）先加上刪除紀錄，之後才完成的擷取也不保存。移除接著在有限時間內等這些擷取，以及發布者要擷取後才知道的單一項目請求，再像使用者刪除一樣逐份刪除訂閱的文件：每份留下刪除紀錄、離開搜尋、記錄自己的事件。超過時限仍在執行的單一項目請求，結束時若文件屬於這個訂閱就刪除。刪不掉的文件計數並保留；移除本身一定完成並記錄事件。

## 狀態

`workStatus` 算出工作狀態，`checkStatus` 加上訂閱自己的狀態算出訂閱狀態；UI 與 Agent 讀同一份，畫面文字在 `src/transport/web/*-presentation.ts`。

- `queued`：還沒開始，冷卻中也是。
- `checking`：列出中，或新增訂閱辨識中。
- `downloading`：收集項目中。
- `retrying`：開始過的工作在等重試或冷卻；檢查的剩餘項目全部在等時也是，時間取其中最早的。

沒有進行中的檢查時，訂閱狀態的優先順序：暫停（使用者或自動）、需要重新登入、已到期待派出、連續失敗、自動檢查關閉、下次檢查時間。還沒有下次檢查時間的訂閱算已到期：排程器在下一輪替它排定時間。

## 重啟後接續

服務停止時，未結束的工作記為中斷，Vault 開啟時在排程開始前接續：

- 較新工作已接手的，以及訂閱已暫停或移除的檢查與其項目，以略過結束。
- 在步驟中途停止達 `MAX_UNCLEAN_STOPS` 次的工作不再接續，以免每次啟動都重演同一個當機；正常關閉不計。
- 其餘工作保留已完成的項目、已保存的文件與已用的嘗試次數。等待條件依工作上的 `wait` 與 `retry` 還原：還沒到時間的繼續等，已過的直接排入。
- 已列出項目的檢查不再列出，等它的項目；還沒列出的，以接續當下的設定與時間列出。
