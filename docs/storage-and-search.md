# 資料儲存、備份、合併與搜尋

> 第一版交付範圍與開發順序見 [YouTube-only MVP 計畫](mvp-plan.md) 與 [GitHub #1](https://github.com/derektu/xr-collector/issues/1)。本文保留產品背景或設計候選；超出該 MVP 的內容不是開工前置條件。

## 文件定位

本文件記錄 vault 儲存與搜尋的概念設計，供後續討論與實作設計使用。第一版聚焦本機 vault 的完整備份、跨機還原與資料合併，以及可由正式資料重建的本機搜尋索引。這些能力不依賴 XQ 的同步或版本協調 server。具體儲存格式、版本管理實作與合併規則尚未定案。

整體架構見 [XR Collector 整體架構](architecture.md)，文件內容與管理資料的分工見 [文件格式與生命週期](document-format.md)。本文涵蓋未來 XR 的資料存取方向；未來內容類型不代表全部納入 Collector MVP。

## 第一版範圍

使用者在本機收集、整理與搜尋知識，也可能在公司與家裡的電腦之間搬移或整合資料。第一版提供兩項能力：

1. **完整備份與跨機還原**：vault 可以完整備份，搬到另一台安裝 Collector 的電腦後還原並使用。
2. **Vault 合併**：將另一份 vault 的資料匯入目前 vault，相同的資料跳過，不同的資料依異動時間順序或使用者選擇處理。

有自動同步需求的使用者，可自行將 vault 放在雲端硬碟的同步目錄。檔案傳輸由使用者選用的工具負責；Collector 第一版不提供跨裝置即時一致性、多人／多機同時寫入協調，也不依賴雲端版本查詢來決定是否允許編輯。同步目錄的實際支援條件需在儲存實作時驗證。

自動 roaming、雲端版本協調及更完整的跨機衝突流程保留為後續方向，不構成第一版的 server 維運需求。XQ 帳號的登入限制與本機備份、還原、合併分開設計。

## Vault 與資料責任

Vault 是可攜的完整知識庫資料單位，包含內容及延續其管理工作所需的正式資料。單獨複製 Markdown 能攜帶文章，但不足以還原完整 vault。

| 資料 | 保存責任 |
|---|---|
| Markdown 正文、frontmatter、附件與保留版本 | Vault 正式資料 |
| 入庫／垃圾桶狀態、刪除紀錄、來源設定、必要的去重與收集進度 | Vault 管理資料 |
| 使用者建立的關聯、derived 的來源依據 | Vault 正式資料 |
| Meilisearch 索引、可重建的查詢與 backlinks 索引 | 各裝置的本機衍生資料 |
| 本機路徑、process 狀態、執行中任務與暫存 | 裝置運作資料 |
| Browser Session、憑證與 API keys | 另行設計保存及跨機使用政策 |

正式管理資料可以保存為 Markdown 以外的結構化檔案；格式與檔案粒度另行決定。本機 database 的使用與責任尚未選定，其中若包含正式資料，就必須納入完整備份、還原與合併的範圍。

所有業務修改先保存到 vault，再更新搜尋或其他本機索引。Meilisearch 不保存任何唯一一份的正式資料。需要保留的搜尋自訂設定，也必須有索引以外的保存來源。

## 完整備份與跨機還原

備份包含 vault 的正式內容、管理資料、附件與保留版本，使使用者能在另一台電腦延續閱讀、整理與搜尋。文件識別與內部關聯在搬移後保持有效，不依賴原電腦的絕對路徑。

搜尋索引與其他可重建的本機資料不必成為備份的必要內容。新電腦還原後，由 Collector 建立需要的索引；來源登入與裝置專屬憑證依其保存政策重新設定，不將原電腦的登入狀態視為跨機使用的前提。

備份應代表可還原的完整資料狀態。備份時如何處理進行中的收集或編輯、如何檢查完整性，以及封裝格式，於實作設計時決定。

## Vault 合併

合併是使用者主動將來源 vault 匯入目前 vault 的操作，不要求雲端登記、指定公司電腦為主機，或先建立 branch。合併涵蓋正式內容與相關管理資料，使文件、狀態與來源關係能共同保存。

| 資料比對結果 | 處理方向 |
|---|---|
| 相同資料 | 跳過，不重複加入 |
| 目前 vault 沒有的資料 | 加入目前 vault |
| 同一份資料有不同內容或狀態 | 依異動時間順序處理，或由使用者決定採用內容 |

「相同資料」的識別、不同文件 ID 卻來自同一來源的去重，以及正文與管理狀態的比較粒度，需要與文件格式設計一併收斂。時間判斷採用哪個異動時間、何時自動採用較新內容、何時交由使用者決定，尚未定案；不能直接把文章發布時間當成使用者修改順序。

合併需要保留衝突處理與復原的空間。刪除與修改並存、時間相同但內容不同，以及異動時間無法可靠比較時的行為，列入後續合併規則設計。

Git 可作為本機版本保存、差異比較及合併的實作候選。第一版的產品契約是完整備份與 vault 合併，不要求使用者理解 commit、branch 或 main trunk；是否採用 Git、如何保存歷史及如何承接沒有共同歷史的 vault，需依上述能力評估。

## Meilisearch 與版本接續

Meilisearch 提供全文搜尋，以及時間、來源與 tags 等篩選能力。此階段聚焦整合，可參考公司既有的繁簡體搜尋設定；不以語言最佳化為前置工作。引擎隨 Desktop 交付，具體 process 或 library 整合方式另行決定。

每台裝置保留自己的搜尋索引。索引跟隨該裝置目前使用的 vault 內容；合併處理正式資料，Meilisearch database 不作為合併的對象。

### 增量更新

Collector 在本機追蹤搜尋索引已處理的資料狀態。一般編輯、收集或 vault 合併後，依實際異動更新受影響的搜尋資料。追蹤方式可依資料版本或異動紀錄設計，不依賴雲端 revision 或特定 Git 模型。

| 目標版本的異動 | 索引處理 |
|---|---|
| 新增文件 | 加入索引 |
| 正文、metadata 或搜尋相關管理狀態改變 | 更新該文件的索引資料 |
| 刪除或不再符合收錄條件 | 移除索引資料 |
| 搜尋資料未受影響 | 保留既有索引 |

例如目前 vault 有十萬篇文件，合併後只有二十篇的搜尋資料受影響，Collector 只提交這些資料所需的索引更新。更新也需涵蓋本機先前尚未完成的異動，不假設合併前索引已完全追上 vault。

Meilisearch 的更新採非同步工作；相關工作成功後才記錄對應資料已完成索引。Collector 需能在中斷或失敗後恢復更新，避免漏掉異動。搜尋設定或索引資料轉換規則也會影響索引有效性，其版本判定與恢復機制另行設計。

尚未解決的合併內容不進入正式索引。索引追趕期間，介面需表達搜尋尚未完全更新；直接讀取文件以已接受的 vault 內容為準，搜尋可見範圍與過渡行為另行決定。

### 重建與成本

新裝置沒有索引、索引損壞，或索引規則變更等情況可能需要完整重建。一般資料合併以增量更新為原則，不要求每次重建全庫。

首次建立、日常批次更新及大幅合併的耗時，需以代表性文件、附件文字量與硬體實測。此階段不承諾重建時間，也不將同步 Meilisearch database 當作必要條件。

## Raw、Derived 與文件關聯

知識庫的資料提供者與內容層次分開表達：

| 提供者 | Raw | Derived |
|---|---|---|
| XQ | 新聞、研報 | Server 邏輯產生的 card、claim／evidence 等資訊 |
| 使用者 | RSS、YouTube 等收集內容 | 使用者透過自訂 template、BYOK 產生的整理內容 |

完整產品的來源方向涵蓋 XQ raw 與使用者 raw；YouTube-only MVP 僅收集 YouTube 既有字幕，各來源交付順序依 roadmap。未來先接入 XQ derived，再擴展使用者 derived；後兩者的產生功能是否屬於 Collector，或屬於整合後的 XR，尚未決定。共同存取介面需能涵蓋這些內容，資料生成責任可由不同流程承擔。

Raw 文件大多獨立存在；關聯可來自使用者明確建立的連結。Derived 則需要表達它依據的原始來源，可能指向多份文件。需要保留的 derived 是正式知識資產，即使可由模型產生，也不能視為搜尋索引般的可丟棄快取。

OKF 提供 Markdown 連結、來源表達與目錄瀏覽的基礎，不會自動建立文件間的知識關係。Collector 解析明確連結並提供 backlinks；語意推論的關聯與共同 tags 不直接當作已確認的來源關係。來源版本定位、claim／evidence 的保存粒度及段落引用方式另行設計。

### Agent 存取與後續研究

Collector HTTP API 的能力方向包含搜尋文件、依穩定 ID 讀取文件，以及瀏覽連結與來源關係。Agent 可透過 Meilisearch 找到入口，再直接讀取文件及其來源；沿已知關聯取文不必重新全文搜尋。具體 API schema 與 Skill 另行設計。

Eval 不屬於此 MVP；以下僅保留未來研究方向，不構成交付或驗收條件。

Eval 比較直接瀏覽 Markdown／grep 與 API 存取的效率，並可將 API 組分為「搜尋＋讀取」及「搜尋＋讀取＋關聯瀏覽」，辨認關聯能力的效益。各組使用相同資料與既有連結，固定模型與預算，評估答案及證據正確性、耗時、token、工具呼叫與無關內容讀取量。

題目涵蓋精確查找、繁簡體、多文件來源追溯及無答案情境；資料同時包含獨立 raw 與具來源關係的 derived。Eval 不預設 API 一定優於直接讀檔。

## 待收斂事項

- Vault 管理資料格式、附件與歷史保存，以及本機 database 的責任。
- 完整備份的範圍、封裝、寫入中資料的處理、完整性驗證及跨機還原流程。
- 相同資料的識別、合併粒度、異動時間定義、自動選擇與使用者決定的分工。
- 刪除與修改衝突、合併結果驗證、復原方式及沒有共同歷史的 vault 合併。
- 本機版本保存是否採用 Git，以及使用者自選同步目錄的支援條件。
- 索引欄位、更新恢復、設定版本、過渡期查詢行為及引擎交付。
- 關聯與來源版本定位、raw／derived 的 API 表達及後續功能範圍。
- 備份／還原／合併的驗證情境、索引更新與 Agent 存取的功能驗收條件。

後續 roaming 可再評估雲端版本協調、跨裝置寫入控制及自動同步；這些機制不作為第一版備份與合併的前置條件。
