# Vault、資料交換與搜尋

Vault 是正式資料，Meilisearch 是可重建的搜尋投影。本文件描述現行資料責任及恢復邊界；操作步驟見 [README](../README.md)，Round 2 的選址、安全搬移與資料交換目標見 [開發計畫](round-2-plan.md)。

## 保存責任

| 資料 | 位置與交換方式 |
| --- | --- |
| Vault 標記檔 | Vault 根目錄的 `xr-collector-vault.json`；不納入 Vault 資料包 |
| YouTube Markdown | Vault 的 `documents/youtube/` |
| 訂閱、各訂閱的收集設定、發現進度與檢查時間 | Vault 的 `settings/youtube-channels.json` |
| 自動收集總開關 | Vault 的 `settings/youtube-schedule.json` |
| 刪除紀錄 | Vault 的 `settings/deleted-documents.json` |
| 附件、保留版本、管理檔案 | Vault 的 `attachments/`、`versions/`、`management/`；隨完整資料包交換 |
| Meilisearch database | 裝置上的搜尋資料目錄；不納入 Vault 資料包 |
| profile、Agent 連線檔與 token | 裝置資料；不納入 Vault 資料包 |
| active Vault 選址 | profile 的 `vault-selection.json`；裝置資料 |
| 收集工作與活動記錄 | profile 的 `jobs/jobs.json` 與 `jobs/events/<UTC 日期>.jsonl`（較早版本的 `jobs/events.jsonl` 照常讀取）；活動記錄保留 30 天；裝置資料，不納入 Vault 資料包 |
| 合併 journal 與合併前備份 | Vault 旁的操作資料，供失敗恢復使用 |
| 上次匯出時間與還原 journal | profile 的 `vault-exports.json`（依 Vault 路徑記錄）與 `vault-restore-journal.json`（進行中還原的暫存資料夾、目標、是否已改名與標記檔雜湊）；裝置資料 |

現行資料使用 Markdown／JSON 與檔案系統，不以 Git 歷史或同步 server 協調 Vault 寫入。同一個 Vault 只由一個程式寫入，外部同步工具不提供多機並行寫入的一致性保證。

## Vault 目錄與選址

每個 Vault 是自成一體的目錄。根目錄的標記檔記錄 `format`（固定為 `xr-collector-vault`）、`formatVersion`、建立時間與建立程式，不含 ID、路徑或其他裝置資訊，因此整個目錄複製到另一台電腦後仍是同一份有效 Vault。程式只開啟 `formatVersion` 不高於自身支援版本的 Vault，較新的格式明確拒絕，避免舊版誤讀。

開啟前先檢查目錄：有效標記檔與可解析的設定檔構成可開啟的 Vault；不存在（上層目錄存在）或只含 `.DS_Store`、`Thumbs.db` 等系統檔的目錄可以建立新 Vault；其他內容一律視為無法辨識。檢查不改動目錄，建立 Vault 只寫入標記檔。

裝置在 profile 記錄目前使用的 Vault 絕對路徑。啟動時若該路徑不存在、變成空目錄、無法讀取或格式無效，服務停在 Not Ready 並回報原路徑與原因，不建立替代的空 Vault，也不啟動排程。選址成功後才建立搜尋 process 與排程。同步資料夾視為一般本機目錄；檔案尚未下載而無法讀取時同樣回報原因。

## 刪除文件

刪除紀錄讓使用者刪除的項目不會被自動收集抓回，跟著 Vault 備份、還原與合併。

### 刪除紀錄的格式

`settings/deleted-documents.json` 是 `{ "version": 1, "deleted": [...] }`，每筆刪除紀錄有：

| 欄位 | 內容 |
| --- | --- |
| `sourceType`、`sourceId` | 穩定的來源識別，例如 `youtube` 與影片 ID；兩者組成文件 ID `<sourceType>:<sourceId>`，同一項目只有一筆刪除紀錄 |
| `sourceUrl`、`title`、`publisherId`、`publisherName` | 刪除時的來源網址、標題與發布者（`publisherId` 可為 null），供合併差異與已刪除文件頁顯示 |
| `deletedAt` | 刪除意圖成立的時間，與文件 frontmatter 的 `collected_at` 由同一個時鐘產生 |

沒有這個檔案表示沒有刪除紀錄。版本不認得、刪除紀錄格式錯誤或重複時，Vault 視為無法開啟並說明原因，不會忽略刪除紀錄而讓已刪除的文件被收集回來。

### 可見性與刪除流程

一份文件有刪除紀錄，且 `collected_at` 不晚於 `deletedAt`（相同時間算在刪除之前）時，列表、閱讀、來源統計、搜尋、匯出與 Agent API 都把它當作不存在。`collected_at` 缺少或無法解析時無法證明文件較新，同樣視為已刪除。

刪除依序寫入刪除紀錄、移除 Markdown 檔案、讓搜尋排除這份文件；刪除紀錄一寫入，刪除就生效，之後的步驟只是清理。索引項目在背景移除，刪除不等待索引重建；移除失敗時記 `document.index_remove_failed` 警告，搜尋仍排除這份文件。

同一項目的保存、索引更新與刪除依序執行，不會交錯：保存後、索引前被刪除的文件不會寫進索引。

開啟 Vault 時、在搜尋索引與 Vault 比對之前，系統處理停止時留下的狀態，並寫入活動記錄：

- 有刪除紀錄又有檔案、`collected_at` 不晚於刪除時間：移除檔案（`document.delete_resumed`）。
- 檔案較新：這是明確重新收集已保存的結果，清除刪除紀錄（`document.recollected`）。
- 檔案的 `collected_at` 缺少或無法解析：檔案與刪除紀錄都保留，文件維持隱藏，並記 `document.delete_unresolved` 警告。

### 收集與重新收集

頻道探索把有刪除紀錄的影片當作已收集，它不會被發現，也不佔補收則數。排程、立即檢查、補收、頻道工作重試失敗影片，以及其他沒有明確使用者請求的收集，遇到刪除紀錄時都結束為 `skipped`，`skipReason` 為 `deleted`。影片工作在擷取字幕前就檢查刪除紀錄，被略過的影片不會向 YouTube 取字幕；保存時再檢查一次，涵蓋擷取期間發生的刪除。

只有使用者以單支網址明確提出、且晚於刪除時間的請求可以重新收集。請求時間取使用者最近一次單獨送出這支影片的時間：直接送出影片網址或重試單支影片的工作，以工作接受的時間為準；同一支影片的工作還在排隊或執行時再次單獨送出，或頻道已排入、使用者又單獨送出，以最後一次送出的時間為準。保存時文件的 `collected_at` 晚於 `deletedAt`，寫入檔案後才清除刪除紀錄；收集失敗時刪除紀錄保留。刪除之前接受的工作，即使在重啟後接續，也不會讓文件回來。

## 匯出與還原

`.xr-vault` 是 version 3 JSON 資料包：檔案使用 Base64，檔案內容與清單以 SHA-256 檢查完整性。匯出套用與列表相同的可見性規則：被刪除紀錄隱藏的文件檔不匯出，文件較新的刪除紀錄也不匯出，所以資料包不會同時有一份文件與隱藏它的刪除紀錄。還原與合併也讀 version 1、2 資料包，這兩個版本沒有刪除紀錄；帶有刪除紀錄檔的 version 1、2 資料包、同一項目同時有文件與刪除紀錄的資料包，以及刪除紀錄格式錯誤的資料包都會被拒絕。合併失敗時復原用的合併前資料包只檢查格式，不檢查文件與刪除紀錄是否一致，復原一定能還原合併前的檔案。只讀到 version 2 的程式會拒絕 version 3 資料包，不會在還原時遺漏刪除紀錄。限制為 128 MiB 包大小、80 MiB 解碼內容、10000 個檔案。系統驗證路徑、衝突、checksum、版本及支援的資料格式；checksum 不等於來源簽章。

資料包頂層可帶 `exportedAt`、`createdBy` 與 `summary`（文件、訂閱、刪除紀錄數），只供比對畫面顯示，不列入清單校驗；讀取時忽略不認得的頂層欄位。文件路徑一律是 `documents/<來源類型>/<來源 ID>.md`，由 `src/vault/document-paths.ts` 依各來源的 ID 規則轉換文件 ID 與路徑；不認得的來源類型或檔案路徑使整包被拒絕。設定檔與文件 frontmatter 中不認得的欄位在還原與合併後保留。

還原在使用者指定的資料夾（不存在或為空，不在目前 Vault 或 profile 內）建立獨立 Vault：先解開到同層的 `<目標>.restoring-<唯一值>` 暫存資料夾並寫入新的標記檔，profile 的還原 journal 記下暫存資料夾與目標；改名為目標之前，journal 先記下「已改名」與新標記檔的 SHA-256。之後建立搜尋索引、寫入選址，選址寫入後刪除 journal，再切換 active Vault。切換前失敗時目標回到原狀、原 Vault 與選址不變。中途停止時，下次開啟 Vault 前依 journal 收回：刪除名稱符合 `.restoring-<唯一值>` 的暫存資料夾；已改名而選址與正在開啟的 Vault 都不是目標時，只有標記檔雜湊相同的目標資料夾會改回暫存名稱並刪除，原本是空資料夾的目標恢復為空資料夾。選址寫入後，切換的收尾（啟動新 Vault 的排程、關閉原 Vault 的排程、工作與搜尋）各自失敗只記錄在程式記錄，還原仍算完成；原 Vault 未完成的收集工作一律記為中斷，原因是切換到還原的知識庫，之後開啟原 Vault 時接續。新 Vault 沒有收集工作。還原保存訂閱、發現進度與各訂閱的收集設定，但自動收集暫停；再次開啟由使用者操作。

匯出、比對、合併與還原期間，程式阻止衝突寫入：開始時先停止派出新的收集步驟，等待執行中的步驟與排程檢查完成。等待期間狀態為 `waiting`，可以取消：不寫入任何資料，狀態回到 `idle`。等待超過 2 分鐘時放棄該操作並回報 `vault_busy`，收集照常繼續；匯出與比對直接以 409 回應，還原與套用合併已先回 202，失敗記在狀態的 `errorCode`。排隊工作在操作期間不開始，結束後接續。

## 合併與恢復

先預覽，再由使用者逐項決定差異。相同項目跳過、新項目加入、來源缺少的本機項目保留；時間戳不自動決定覆寫。匯入包缺少某份文件不表示刪除。

刪除紀錄以文件 ID 比對，列為 `deletion` 類項目：一方有記錄、另一方有同一份文件時是衝突，只列這一項，不另列文件項目；採用匯入的記錄會移除本機文件與索引項目並加入記錄，採用匯入的文件會寫入文件、清除本機記錄並建立索引。只有匯入包有記錄、本機沒有這份文件時，記錄直接加入；兩邊都有記錄時相同。合併移除的文件在套用失敗時與其他檔案一起從合併前資料包復原。頻道以 ID 比對，名稱、網址、暫停狀態或收集設定不同即列為該訂閱的衝突；發現進度與檢查時間不算差異。採用匯入的訂閱時套用這些欄位，發現進度（游標、最近檢查、補收中）保留本機，下一次檢查從合併後起算；本機沒有的訂閱連同匯入的發現進度加入。自動收集總開關屬於被合併的 Vault，不列入比對。附件與管理檔案以路徑及內容比對。套用前重新比對本機與匯入包，核對每個項目的狀態與本機內容（文件與檔案的位元組、刪除紀錄、訂閱的名稱、網址、暫停狀態與收集設定）是否與預覽相同；不同時要求重新預覽。訂閱的發現進度與檢查時間不在核對之列，預覽後排程照常檢查不會讓預覽失效。

### 訂閱設定的格式版本

`youtube-channels.json` version 2 是 `{ "version": 2, "channels": [...] }`，每個訂閱帶 `settings`（`intervalMinutes`、`backfillWindow`、`backfillMaxItems`）、`nextCheckAt` 與 `lastDispatchedAt`；`youtube-schedule.json` version 2 有 `enabled`，轉換過的 Vault 另有 `legacySettings`：轉換時給每個訂閱的共用設定，只供轉換前接受、尚未建立訂閱的新增訂閱工作使用，讓它與同一 Vault 的其他訂閱一致；沒有這個欄位時，這類工作從接受時的首次收集範圍推回補收設定，頻率用預設值。Version 1 的頻道檔是陣列，所有訂閱共用 version 1 排程檔的頻率與補收設定。

Vault 開啟時與資料包解開後，version 1 的頻道檔轉成 version 2：共用設定與檢查時間複製到每個訂閱，共用設定另存為排程檔的 `legacySettings`。是否轉換只看頻道檔版本；頻道檔先寫，排程檔後寫，兩次寫入之間中斷時不會重轉，殘留的 version 1 排程檔只讀總開關。舊版程式讀到 version 2 的頻道檔或資料包時明確拒絕，不會改用共用設定。

有實際異動時，先建立合併前資料包與 journal。套用失敗會復原檔案及搜尋；復原失敗則保留恢復資料、停止寫入與排程，重啟先處理 journal。合併期間文件／搜尋 API 暫時拒絕存取，狀態 API 仍可查詢。備份及 journal 在恢復完成前必須保留。

## 搜尋投影

收集先保存 Markdown，再更新索引。索引失敗不刪除已保存文件；列表與全文可從 Vault 讀取，搜尋依索引狀態回報結果或錯誤。成功合併只對新增／替換文件更新索引；還原使用獨立索引。

索引名稱帶 schema 版本（`documents_v2`）；schema 改變時使用新名稱並從 Vault 全量重建，舊版本的索引在啟動時刪除。每筆索引文件的 key 是完整文件 ID 的 base64url 編碼，不同來源類型即使來源內 ID 相同也不會互相覆寫。來源篩選使用 `sourceType` 與 `publisherId`；頻道名稱只供顯示與搜尋，不作篩選條件。

每筆索引文件帶有其 metadata 與正文的內容雜湊。啟動時逐筆比對索引與 Vault 的文件 ID 及雜湊，集合或任一雜湊不同就從 Vault 全量重建，因此篇數相同但內容或身分不同時也會重建；完全一致時沿用持久化索引。全量重建完成的時間記錄在裝置的搜尋資料旁（`<搜尋資料目錄>-state.json`），供設定頁與 `GET /api/search/status` 顯示。這項比對只在啟動時進行；執行期間的收集逐筆更新索引。

刪除文件時，文件 ID 先加入待移除清單，再在背景從索引刪除。搜尋時清單內的 ID 以引擎篩選條件排除，結果與總數都不含已刪除文件。索引刪除失敗時 ID 留在清單，下一次索引異動時再刪除；清單超過 100 筆時改為從 Vault 全量重建，篩選條件因此維持在固定長度內。清單只存在於執行中的程序；重新啟動後，啟動時的比對會發現索引多出已刪除的文件並全量重建，重建完成前搜尋不提供結果。

Meilisearch 的 dump／snapshot 是引擎運維產物，不是 `.xr-vault`，不作為 Collector 跨機資料交換格式。
