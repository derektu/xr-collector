# 開發驗證流程

每張票在實作前列出驗收 scenario，實作後在執行中的 App 上逐一驗證；build 或 CI 通過不能代替行為驗收。

本文件是跨專案共用的流程。本專案的指令、驗證層級、平台、門檻內容與打包規則見 [專案驗證設定](project-validation.md)；一張票怎麼從談設計走到 merge 見 [做一張票](worker-workflow.md)。

驗證有兩種用途，成本分開算：

- **做票驗收**證明本票的新行為。嚴格、涵蓋邊界，只在這張票做一次。
- **回歸**防止之後的修改弄壞核心行為。每次 merge 都跑，所以要小、快、穩定。

做票驗收寫的 scenario 不會自動變成回歸檢查。

## 測試深度看後果

- **嚴重**：資料遺失或毀損、不可逆的操作、機密外洩，或專案的核心保證被破壞。測到邊界情況。
- **可恢復**：最壞只是一次操作失敗，使用者重試即可。涵蓋主要路徑；下層測試已涵蓋時不另外測。

## 1. 驗收計畫

實作前寫在票面。每個 scenario 寫出：

- **防什麼**：壞掉時使用者會遇到什麼
- **層級**：能證明它的最低一層（單元、整合／API、畫面）
- **預期結果**：可以檢查的條件（數量、狀態序列、值），才能寫成斷言
- **平台**：只在行為依平台而不同時寫

只列本票的風險。只是照規格走一遍主要路徑、或下層測試已涵蓋的 scenario 不列。相關的 scenario 串成一條流程，前一個的結束狀態就是下一個的起點，不各自重建資料。

規則與狀態邏輯放在單元或整合測試；畫面與端到端流程只涵蓋必須把多個 module 串起來才看得到的結果。票沒有改畫面、但改到畫面依賴的狀態或資料流時，仍跑對應功能的回歸流程，因為各 module 的單元測試各自通過，不代表畫面上的狀態正確。

需求或 scenario 在開發中改變時，先更新票面的計畫與預期，再驗證。

## 2. 執行

- **斷言要能失敗**：證明新行為的斷言，在沒有修正的程式上必須失敗。修正完成後保留測試、拿掉修正跑一次，交付時附上失敗的輸出。改了既有的斷言時同樣確認，因為語意改變時既有測試常變成恆真而不報錯。
- **斷言讀狀態，不比對文字**：讀 API 回應、存下的資料與結構化的 DOM 屬性，不比對整句畫面文字。資料面的狀態直接讀資料本身，不只經過本票修改的 API。截圖只負責版面與視覺，每張都看過再判定，確認不是錯誤頁、過期畫面或空白。
- **等狀態，不等時間**：不用固定 sleep。等待經共用的 helper，上限統一；由測試擋掉直接睡眠與個別調長上限。上限是狀態一直沒出現時多久報錯，不是預期耗時。
- **查根因**：沒有改程式卻失敗時，歸為產品 bug、測試假設或環境並查到原因，不以重跑、拉長 timeout 或改分類讓它消失。當下修不了的開票。
- **不符合預期的觀察要回報**：執行時看到與規格或一般使用習慣不一致的地方，例如畫面文字、等待時間、狀態、排版，屬於本票範圍就修正後重跑，否則列為待使用者決定的問題，附截圖與實際觀察，不寫成備註帶過。scenario 全部通過不代表沒有這類問題。
- **結果對應受測的版本**：交付的結果記錄受測的 commit 與未提交內容；程式改了就重跑受影響的 scenario。執行測試的指令保留 exit code。

## 3. 回歸流程

一個 scenario 同時符合兩點才收錄為回歸流程：

- 是核心使用路徑，或壞掉的後果嚴重
- 下層測試抓不到

每個測試檔與回歸流程開頭寫出它防什麼：壞掉時使用者、Agent 或開發者會遇到什麼；只防開發者的標明 “Guards the developer, not the user”。說不出防什麼的不留。

功能地圖列出每個功能由哪些回歸流程涵蓋。做票時從本票改到的功能查出要跑哪幾支，驗收計畫列出要跑的流程；功能相關但不跑的寫出原因。

## 4. 門檻

- **merge 門檻**：全部自動檢查，加上專案指定的回歸流程。要快、結果要穩定。
- **完整驗證**（nightly 或發布前）：慢的或依賴環境的項目，例如全部流程、其他平台、打包、真實的外部系統。

門檻變慢或測試變多時，停下來逐項檢討：保留、合併、移到下層或刪除，不一直往上疊。

## 5. 審查與交付

審查由沒有參與實作的 reviewer 進行。reviewer 只拿 diff、票面與 repo，不拿實作者的結論，才看得出實作者看漏的地方。審查分三個面向，分開回報：

- **正確性與風險**：從每個改動追到受影響的 module，檢查是否弄壞既有功能、有無安全問題、是否改變開發者建置或執行的方式，以及只該在特定條件開啟的功能是否外漏。
- **需求與規範**：對照票面原文與專案規則。
- **module 的深度**：新增或加寬的介面是否藏住了足夠的實作；功能是否長在既有 module 的介面後面，而不是在同一層多開一個平行的 module、讓呼叫者自己去串；依賴是否只往介面走，沒有穿過介面直接拿 module 的內部。

reviewer 只回報追到底、確定成立的問題。不修的問題與理由列為待使用者決定的問題。

交付列出：

- 受測的 commit、CI 結果，以及需求平台與實際驗證的平台
- 每個 scenario 的結果（pass／fail／blocked）與實際觀察
- 新斷言能失敗的證明
- 第 2 節每一條不符合預期的觀察，以及處理方式（已修正並重跑，或待使用者決定）
- 待使用者決定的問題
- 沒有驗證的項目與原因

證據放在本機的 `.local/ticket-artifacts/<issue>/`，不進 git，也不上傳 PR。畫面改版後只留最新一份。
